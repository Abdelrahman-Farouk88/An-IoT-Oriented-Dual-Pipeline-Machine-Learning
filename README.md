# Reproducibility release: IoT-oriented dual-pipeline framework

This directory accompanies the revised manuscript:

> **An IoT-Driven Machine Learning Framework for Predictive Backorder Management and Intelligent Logistics Optimization**

The title is retained from the submitted manuscript. The evidence in this release is
more narrowly scoped: it validates two predictive components and a simulation-based
maintenance--inventory testbed; it does not validate an end-to-end field deployment or
a product-to-part linkage.

It contains the experiment scripts, selected derived result files, LaTeX tables, and paper figures. It does **not** redistribute the two public datasets. Instructions for obtaining them are in `data/README.md` and `CMaps/README.md`.

## What the code reproduces

- **IoT pipeline (NASA C-MAPSS FD001):** causal, per-engine ARIMA residual features; causal rolling features (no future cycles); engine-grouped 5-fold cross-validation; a 70/30 engine-grouped holdout; a paired 45-versus-48-feature ablation; permutation importance and SHAP.
- **Cross-subset replications and strict transfer:** FD002, FD003, and FD004 using the same 15 FD001 sensor channels and the same 48-feature schema. Models are retrained on each subset's training engines with fixed hyperparameters. A separate strict transfer test freezes FD001 preprocessing, ARIMA orders, feature schema, and models, and uses no target labels; macro F1 degrades sharply on FD002 and FD004.
- **Backorder pipeline (public Kaggle data):** a 42-configuration resampling/classifier screen on a 240,000/60,000 split of the 300,000-row training subset; five-fold cross-validation of the top three configurations and three prespecified baselines; one-time evaluation on the official 242,075-row test split; bootstrap CIs; McNemar and DeLong tests; precision-recall/AP; Platt calibration; cost-sensitive thresholds; base-rate prior correction; permutation importance and SHAP.
- **Simulation-based maintenance--inventory study:** a discrete-event inventory simulation with 100 assets, five SKUs, five lead-time profiles, 600 cycles, and an explicit random asset-to-SKU mapping. The main study uses Pipeline A risk trajectories only. Reactive, calendar, risk-triggered, and oracle replacement policies are evaluated under common random numbers across 20 held-out seeds, with a sensitivity analysis over failure cost and lead-time scaling. A secondary B-informed controller queries Pipeline B through a stated state-to-feature mapping; it is a surrogate and reports a null cost result against a shuffled control.
- **Paper artefacts:** the fourteen LaTeX table files in `tables/` (plus three inline tables) and the thirteen figures used in the manuscript in `figures/` (PDF and PNG).

The paper reports a null result for the three ARIMA residual features: the 45-versus-48 ablation is not statistically detectable. The code retains that comparison. It also reports negative strict transfer and a neutral B-controller result; both are reproduced from the saved artefacts.

## Environment

Tested with Python 3.13.2 on Windows 11 with the package versions in `requirements.txt`:

```text
numpy 2.3.3
pandas 2.3.2
scikit-learn 1.9.0
xgboost 3.4.1
imbalanced-learn 0.14.2
statsmodels 0.15.0
scipy 1.18.1
shap 0.54.1
matplotlib 3.10.6
seaborn 0.13.2
joblib 1.5.3
```

Create an isolated environment and install the dependencies:

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
```

All random seeds are fixed to `42`. `BO_N_JOBS` (default `4`) controls the number of parallel jobs in the backorder pipeline; `N_JOBS` in `iot_revision.py` is also `4`. Reduce these values on machines with limited memory.

## Data layout

Place the public files at the following paths, relative to this directory:

```text
CMaps/
  train_FD001.txt
  train_FD002.txt
  train_FD003.txt
  train_FD004.txt

data/
  Training_BOP.csv
  Testing_BOP.csv
```

The scripts expect the original whitespace-separated C-MAPSS training files and the original Kaggle CSV files, including the header row of the backorder data. The `sku` column is dropped by the backorder pipeline because it is a unique row identifier, not a product key.

See `CMaps/README.md` and `data/README.md` for source and licence notes. The datasets are not included here. The simulation study needs no additional external data; it reads the risk curves in `results/sim_risk_curves.csv`. Trained model artifacts (`results/models/iot_fd001.joblib` and `results/models/bo_final.joblib`) are regenerated by `iot_revision.py` and `bo_revision.py` and are not shipped, to keep the archive small; `iot_transfer.py` and `b_inventory_simulation.py` require those regenerated models.

## Running the experiments

Run commands from this directory (the scripts resolve paths relative to their own location).

### 1. IoT pipeline

```bash
python iot_revision.py --only all
```

This performs the FD001 analysis and then the cross-subset FD002-FD004 replications serially. To run only one part:

```bash
python iot_revision.py --only FD001
python iot_revision.py --only external
```

The per-engine ARIMA residual computation is the runtime bottleneck. A parallel cross-subset runner is provided:

```bash
python iot_external_parallel.py
```

It uses the same splits and seeds as `iot_revision.py` and writes the same `results/iot_FD00*.json` files.

Run the strict frozen FD001-to-FD002--FD004 transfer test:

```bash
python iot_transfer.py
```

It caches the target feature matrices, reuses the frozen FD001 models in
`results/models/iot_fd001.joblib`, and writes `results/iot_transfer_results.json`,
`results/iot_transfer_features_FD00*.csv`, and
`results/iot_transfer_predictions_FD00*.csv`.

After the FD001 run has written `results/iot_features_FD001.csv`, run the paired ablation:

```bash
python iot_ablation.py
```

Verify that the ARIMA residuals are causal (future observations do not affect earlier residuals):

```bash
python test_causality.py
```

### 2. Backorder pipeline

```bash
python bo_revision.py
```

This is the longest step. It writes the validation grid, cross-validation folds, final predictions, calibration/cost artefacts, permutation/SHAP outputs, and `results/bo_revision.json`. It reuses `results/bo_validation_grid.csv` if that file exists, so an interrupted run can resume after the screening stage. Delete that file to force a fresh 42-configuration screen.

### 3. Simulation-based maintenance--inventory study

The simulation consumes the out-of-fold XGBoost risk curves in
`results/sim_risk_curves.csv` (all 100 FD001 engines: OOF predictions for the 70
training engines plus holdout predictions for the 30 test engines). The file can be
rebuilt from `results/iot_oof_48_xgb.npy`, `results/iot_holdout_predictions.csv`, and
the FD001 feature matrix produced by `iot_revision.py`.

```bash
python integrated_simulation.py --mode quick        # one-seed sanity check
python integrated_simulation.py --mode tune         # 10 training seeds, full grid
python integrated_simulation.py --mode final        # 20 held-out seeds
python integrated_simulation.py --mode sensitivity  # failure-cost and lead-time scenarios
python b_inventory_simulation.py                    # B-informed controller tuning/test
python make_sim_outputs.py                          # Tables 15-17 and Figures 11-13
```

`tune` writes `sim_tune_<policy>.csv` and `sim_best_configs.json`; `final` writes
`sim_test_runs.csv` and `sim_test_summary.json`; `sensitivity` writes
`sim_sensitivity_runs.csv`. `make_sim_outputs.py` requires those files plus
`sim_risk_curves.csv`. The selected configurations are stored in
`sim_best_configs.json`, so `final` and `sensitivity` do not repeat the tuning search.
`b_inventory_simulation.py` writes `results/b_inventory_tuning.csv`,
`results/b_inventory_test_runs.csv`, and `results/b_inventory_summary.json`; it uses the
champion backorder model in `results/models/bo_final.joblib`.

### 4. Tables and figures

```bash
python make_tables.py
python make_figures_revision.py
```

`make_tables.py` uses the result JSON/CSV files in `results/` and writes the ten component tables to `tables/`; `make_sim_outputs.py` adds the three simulation tables (Tables 15--17). The mapping table `tab_b_mapping.tex` is included directly.

`make_figures_revision.py` uses both the saved result files and larger intermediates produced by the pipelines (`iot_features_FD001.csv`, `iot_curve_*.npz`, `bo_curves.json`, `bo_oof_predictions.csv`). Those large intermediates and the full prediction files are omitted from this release to keep it small. The figure PDFs used in the manuscript are included in `figures/`; rerun the pipelines first if you need to regenerate them from scratch.

## Scope and caveats

- C-MAPSS is a simulation-generated benchmark, not field data.
- The two pipelines are independently validated components. Their integration is a proposed blueprint, not an end-to-end validated logistics system.
- Cross-subset replications retrain within each target subset. The strict frozen FD001 transfer test degrades sharply on FD002 and FD004; it does not support cross-dataset generalization.
- The backorder task is row-level; the Kaggle `sku` field cannot support product-grouped validation.
- No field deployment or real-time control is claimed. The simulation tunes $(s,Q)$ only within the testbed; it is not a field-validated inventory policy or a general logistics optimization.
- SHAP and permutation importance are associational, not causal.
- Cost-sensitive thresholds are selected on out-of-fold predictions and reported as sensitivity analyses, not deployed operating points.
- The main maintenance--inventory study uses Pipeline A risk trajectories only. The secondary B-informed controller is a surrogate based on a hand-specified state mapping; it does not improve cost and is not evidence of a validated product-to-part link. The simulation uses a random asset-to-SKU mapping and illustrative costs; it is not field validation or a record-level merge.
- The risk-triggered policy records zero simulated failures at the tuned threshold; this is a simulator and threshold artefact, not evidence that failures cannot occur in practice.
- The 9.8% oracle gap quantifies the cost of imperfect prediction in the simulator, not an optimality guarantee.
